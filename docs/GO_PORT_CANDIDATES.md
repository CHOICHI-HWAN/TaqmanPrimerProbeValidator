## 포팅이 아니라 캐시가 답인 곳 (서버 응답 지연)

| API | 시간 | 병목 |
| --- | --- | --- |
| `/api/overview` | 1.4~1.9초 | TSV를 매 요청 다시 읽음(`csv` 5.9만 행 0.5초) + `host_scope` 행별 분류 0.5초 |
| `/api/venn/s` | 0.8~1.1초 | 같은 TSV 재읽기, 세트별 통과 목록 재계산 |
| `/api/groups/<id>` | 0.6초 | 같은 원인 |

이 병목은 언어가 아니라 **매 요청 재계산**입니다. 파일 수정시각(mtime)을 키로 한 파싱 결과 캐시가 Go 포팅보다 이득이 크고 위험이 작습니다(Go로 옮기려면 파이썬 서버와 프로세스 통신 비용이 생김). 별도 작업으로 권합니다.

## 포팅하지 않을 것

Snakemake 규칙, MAFFT·MFEprimer·pixy·varVAMP·PrimerHunter 호출, 리포트 PDF, 웹 서버 전체. 병목이 외부 프로그램이거나 입출력이라 이득이 작고, 두 프로젝트(LASV·NiV)를 같이 유지하는 비용만 늘어납니다.

## 진행 방식

1. 후보마다 `go/<이름>/` 작은 CLI(JSON in/out) + `-selftest`.
2. `scripts/engine_check.py`에 비교 케이스를 추가하고 `🧪 엔진 검증` 메뉴에 표시.
3. 실제 세트 전부 + 합성 데이터에서 차이 0건이 되면 속도를 재고, 이득이 있을 때만 파이썬에서 선택적으로 호출(기본은 파이썬 유지).
